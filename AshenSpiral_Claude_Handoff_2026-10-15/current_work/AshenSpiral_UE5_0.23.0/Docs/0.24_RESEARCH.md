## 1. Headline findings

1. **Ready orb (A2): root cause found, high confidence.** 0.23.5 deleted the Ready card and READY text from the menu, but the hub *station* that draws the glowing orb and the "THE SPIRAL / Expedition / Ready" label is still defined in the world (`Private/ASWorld.cpp:283`).
2. **Flying boss "moonwalk" (A6): root cause found, high confidence.** The boss is Kind 4, which gets the humanoid armour rig, and the walking gait is driven by velocity. It orbits while facing its target, so its feet run sideways and backwards in mid-air.
3. **Flying boss can't be meleed (A7), found by arithmetic.** At its normal hover it sits 242 cm above the player's centre. The melee vertical tolerance is 230 cm.
4. **Max-range arcs (A3): the premise doesn't match the code.** The 0.23.4 gold ring was deliberately removed in 0.23.5 and replaced with a crosshair cue, so there is no max-range floor arc to render. The order needs one clarification (open question 2).
5. **P2 invisible walls (A1): not root-caused.** No P2 `AshenNetBase` data exists yet. The code shows each machine builds the arena itself from replicated data, and the build/protocol version was never bumped, so mismatched builds can join each other. Layout or collision-state disagreement between machines is still the strongest lead, but the build-mismatch explanation is largely ruled out (P2 ran the same package), so the shift-timing hypotheses (H2, H3) now lead.
6. **Lightning circle (A8) looks like enemy telegraphs because it is built the same way.** Same ring mesh, near-identical red/orange palette.
7. **Two unreported bugs found.** The sniper's aiming beam can never show (a `//` comment swallowed the call). The Broodcaller stops summoning after two attacks.
8. **The project has no skeletal meshes and no animation assets at all.** Enemy "animation" is a 21-part static-mesh rig posed by code. This shapes every Part B option.
9. **Several Crab Champions recon claims did not hold up** (Part C): "Barrel Skull", "Deja Vu", the +1000% knockback buff and the Spiffing Brit luck video were not found, and slide is documented as a speed boost, not a dodge.

## 2. Part A - the 11 fix items

### A1. P2 invisible walls persist (P2-only)

**Status: not root-caused.** I can't give a proven cause without runtime evidence.

**Diagnostic status.** The `AshenNetBase` hunk is in the working tree (uncommitted) in `Private/ASGameMode.cpp`, built into the editor DLL (confirmed the string is in the binary). The only line collected so far is the host's own login: `ASCharacter_0 base=none mobility=-1 netOk=-1` **[LOG]**. No P2 has joined that session yet. Note the diagnostic reports *movement bases*. It cannot see arena layout, which is where my leading hypothesis sits (below).

**A related join failure I did see (two reproductions) [LOG].** A client joining the editor host was dropped about 200 ms after "Join succeeded": the server warned `FNetGUIDCache::SupportsObject: HierarchicalInstancedStaticMeshComponent ... ASWorld_0.HierarchicalInstancedStaticMeshComponent_NN NOT Supported`, then received `ActorChannelFailure` on channel 6 (an `ASEnemy`), then closed with `ControlChannelClose`. Cause unproven. It happened with an editor host, not the packaged playtest, so it may be a different bug from the invisible walls.

**What the code does (all [CODE]):**
- Arena geometry is **not replicated**. Each machine rebuilds it locally from the replicated `Config` (Seed, Shuffle, Keep positions, Generation, Epoch) through `ASRules::EndlessProps(Seed ^ Shuffle*7919, Keep)` (`Private/ASWorld.cpp:325`). `Config` is the only replicated field (`ASWorld.cpp:54`) and its RepNotify is `Rebuild` (`Public/ASWorld.h:34`, `UPROPERTY(ReplicatedUsing=Rebuild)`), so a client rebuilds the moment the config arrives. The `Tick` poll (`ASWorld.cpp:128-135`) is only a safety net that logs a warning when it fires.
- *Correction (2026-10-18, found while building 0.24):* an earlier version of this section said `Config` had no RepNotify and that clients rebuild by polling. That was wrong; I had searched for `OnRep_` names and missed that the notify function is called `Rebuild`. Host and client both use the cover-only path on a shuffle (`ASWorld.cpp:218`). P2's zero "safety rebuild" lines are therefore the *expected* result, not evidence about H2 either way.
- Visual blocks (`EndlessCover*`) and collision proxies (`EndlessSolid`) are separate hidden/shown batches. The animation only moves visuals vertically (`SetRelativeLocation(0,0,-Drop)`, `ASWorld.cpp:201`). Collision is toggled for all proxies at once (`SetCoverCollision`, `ASWorld.cpp:176`).
- The collision on/off decision is made **locally on each machine** from its own smoothed clock and its own view of where heroes stand (`ASWorld.cpp:186-196`).
- Runtime HISM components are created with `NewObject` (`ASWorld.cpp:232`), so they have auto-generated names and are not net-addressable.
- **Versions never changed:** `ProjectVersion=0.23.2` (`Config/DefaultGame.ini:5`) and `Protocol = 2300` (`Public/ASData.h:125`, checked at `ASGameMode.cpp:77`). The editor log prints the same `AshenSpiral 0.23.2` for 0.23.2 and 0.23.5 code. A 0.23.2 build and a 0.23.5 build can therefore join each other without any rejection. Packages for 0.23.2, 0.23.5 and 0.23_P2 exist under `C:\Games\`.

**Reasoning [INFER].** The animation only moves blocks *vertically*, but the report is a *horizontal* offset between what P2 sees and what blocks them (the "large square shape"). P2's own visuals and P2's own collision are built from the same local data, so they can't disagree with each other. What can disagree is **P2's layout versus the host's**. The server corrects P2's movement against the server's layout, so P2 walks through walls that look solid on P2's screen and hits walls that don't exist there. That points to a layout mismatch between machines, not to the animation.

**Ranked hypotheses:**

| # | Hypothesis | Confidence | Cheap check |
|---|---|---|---|
| H1 | ~~P2 ran a different build than the host~~ **Largely ruled out:** Josue confirmed P2 ran the same package (2026-10-18). Residual: a package that mixes stale files is still conceivable but unlikely | low | None needed unless H2-H4 also fail |
| H2 | Layout swap timing: the client rebuilds when the `Config` RepNotify arrives, on its own smoothed clock, while the server's shift timeline is already running, so for a window the two machines hold different layouts or collision states | low-medium | Log `Seed/Shuffle/Generation/Epoch` plus a footprint hash on both machines at each shift |
| H3 | Local collision toggle disagrees across machines while a hero overlaps a footprint (hold-off uses each machine's own hero positions) | low-medium | Log `SolidState` transitions on both machines |
| H4 | The same unresolvable-net-reference family as the join failure, applied to world geometry | low | `AshenNetBase` lines once P2 joins |

**About the "safety rebuild" log line:** `AshenVisual: client geometry safety rebuild %d (generation=...)` (`ASWorld.cpp:133`) is printed only when the Tick safety net has to repair geometry the RepNotify did not build. Its absence from P2's log (confirmed: zero hits) means the RepNotify path worked, which says nothing against a collision-state disagreement (H3).

**Cleared hypothesis.** I checked whether `CoverFootprints` could accumulate stale entries across shuffles. It can't: `BuildEndlessCover` resets it first (`ASWorld.cpp:321`).

### A7. Flying boss goes underground / out of the map

**Contributing causes found; exact trigger not proven (medium-low).**
- Fliers have **no world collision**: `RefreshLook` sets the capsule to ignore `WorldStatic` and `WorldDynamic` (`ASEnemy.cpp:73`). Nothing clamps the orbit to arena bounds. The orbit is centred on the *target* at a 760 cm radius (`Public/ASExpeditionRules.h:228`), so a player near an edge puts the orbit outside the walls.
- The "fell below the map" rescue (`ASEnemy.cpp:187`) sits *after* the `Flies()` branch that returns (`ASEnemy.cpp:186`), so it never runs for fliers.
- Hover height is computed from the **target's** Z (`FloorZ = There.Z - 88`, `ASEnemy.cpp:358`), not the arena floor.
- At spawn the boss's capsule has a half-height of about 201 cm and spawn protection holds it in place for 2 s (`ASEnemy.cpp:170`). Whether it spawns half-sunk into the floor depends on the spawn point's height, which I didn't verify.

**Melee reachability finding [CODE + arithmetic].** Hover is 330 cm and the target offset is -88 cm, so the boss orbits about **242 cm above the player's centre**. Melee requires the vertical difference to be under **230 cm** (`Private/ASMeleeCombat.cpp:70`). So while orbiting, the boss is above melee tolerance and can be hit only when the player is higher (jump/leap) or during a dive. The Gloomwing hovers at 200 cm and is within tolerance.

Evidence needed: log boss Z against target Z each second during a flying-boss fight.

### A9. On-hit rewards should scale by swings/sec, per weapon

How the current reward code works [CODE]:
- On-hit rewards live in `HitProcs` (`Private/ASCharacterUpgrades.cpp:114-145`), called per enemy hit. Element procs, stun and root use `ProcChance(rank, perRank)` (`Public/ASBuildRules.h:175`), which depends only on trait rank and is capped at 75%. It does **not** depend on the weapon.
- Several rewards have hard internal cooldowns: Leech 0.25 s, Conduit 0.15 s, Shock 0.35 s, Chain 0.35 s. At fast fire rates these caps, not the fire rate, limit rewards.
- Ranged weapons already normalise multi-hit shots: only the first hit carries a proc (`ProcAvailable`, `ASSpell.cpp:52-60`). Melee procs once per target hit, so cleaving several enemies triggers more.
- Attack speed: `AttackSpeed = 1 + .08*permanent + .12*run` (`Public/ASRules.h:42`); interval = `Base / AttackSpeed` (`ASRules.h:43`); the menu already shows live swings/s (`SASMenu.cpp:44-45`).
- Base intervals (seconds) and elements, from `Public/ASArsenalRules.h:8` and `Private/ASData.cpp:5-14,111-113`:

| Weapon | Element | Base interval | ~Attacks/s (base) |
|---|---|---|---|
| Cinder Blade | Burn | 0.28 | 3.6 |
| Grav Hammer | Frost | 0.72 | 1.4 |
| Ash Bow | Poison | 0.30 | 3.3 |
| Spiral Glaive | Frost | 0.48 | 2.1 |
| Ember Staff | Burn | 0.34 | 2.9 |
| Rift Scythe | Poison | 0.40 | 2.5 |
| Cinder Scattergun | Burn | 0.72 | 1.4 |
| Tempest Rotary | Frost | 0.105 | 9.5 |
| Rift Mortar | Burn | 1.05 | 1.0 |

Melee combos apply an additional per-step time scale (`ASMelee::TimeScale`), so real melee rates differ from these numbers.

Consequence [INFER]: because chance doesn't vary by weapon, the Rotary lands about 9x the procs per second of the Mortar at the same trait rank.

Ambiguities to settle before planning (open question 6): which rewards count as "on-hit rewards", and whether "swings/sec" means the weapon's base rate or the live rate.

## 3. Part B - Enemy rework research

### 3.1 Roster audit

**Shared behaviour for every grounded enemy** (`Private/ASEnemy.cpp:156-239`):
- Targets the **nearest non-downed hero by flat distance**. No threat, role or aggro variation.
- Loop: re-route every 0.25 s along the arena nav grid; walk; if in range with clear sight and off cooldown, **wind up** (stop moving), then **commit** the attack, then 1.8 s cooldown (2.0 s for bosses).
- **No kiting, strafing, flanking, retreat, or keep-distance.** Between attacks even ranged enemies keep walking toward the player until about 145 cm. The speed bonus (`ApproachScale`, `Public/ASMeleeRules.h:63`) only speeds enemies up when far.
- Local separation steering keeps bodies apart (`ASEnemy.cpp:217-223`).
- Stuck recovery: after 3 s of no movement and more than 600 cm from the target, the enemy is teleported (`ASEnemy.cpp:226-236`).
- Base HP: 70 + 22 per ward; elite 300; boss 1100 + 450 per ward. Multiplied by 1.45 in two-player, and by kind: Bulwark 1.8, Broodcaller 1.5, Leaper 0.85, Gloomwing 0.55 (`ASGameMode.cpp:369-370`). Endless cap 36 enemies, story cap 42.
- Spawn pools unlock by room or wave (`ASGameMode.cpp:365-367, 452-455`).

### 3.2 Animation feasibility in UE 5.8

**What exists today [CODE]:**
- **Zero skeletal meshes, zero animation assets, zero AnimBPs.** Content is 78 static meshes (OBJ imports), 12 textures, 12 sounds, 1 material.
- Enemies are a **21-part static-mesh armour rig** posed by code each frame: 2-bone limb IK (`ASPose::Limb`), a foot-placement gait (`ASAnimation::Foot`), windup lean, a release gesture, hit-reaction recoil and a topple-and-fade death (`Private/ASEnemyAnimation.cpp`). The engine's own character mesh is hidden (`ASEnemy.cpp:26`).
- Kinds 5 and 9 skip the armour rig entirely (squash and stretch only). The flier flaps two wing slabs.
- Animation inputs are already **replicated timing fields** (`WindupStart/End`, `AttackReleaseTime`, `HitReactionTime/Strength/Direction`), so clients animate cosmetically with no extra network cost.
- The player cape already has a node-based cloth sim (`Public/ASAnimationRules.h:66`), and an `SM_EnemyCape` mesh exists. That sim is a reusable pattern for enemy cloth.

**What UE 5.8 provides on this machine [verified by listing `C:\Program Files\Epic Games\UE_5.8\Engine\Plugins`], none enabled in `AshenSpiral.uproject`:** ControlRig, IKRig, PoseSearch (Motion Matching), AnimationWarping, MotionWarping, PhysicsControl, AnimToTexture, AnimationBudgetAllocator, RigLogic, Mover, StateTree, SmartObjects, MassGameplay, GameplayAbilities, LearningAgents. The engine's `TP_ThirdPerson` template also ships the Manny mannequin with combat animation blueprints (`ABP_Manny_Combat.uasset` found). I haven't opened the editor, so nothing below is tested. Licence terms for template content need checking before any shipping use.

**Paths, with rough relative cost (my estimates, unmeasured):**

| Path | What it is | New assets | Relative cost | Meets "every attack has an animation"? |
|---|---|---|---|---|
| P1 | Extend the current procedural rig: data-driven pose tracks per attack (anticipation, strike, recovery curves), more IK targets, squash and stretch, hit-stop | none | S-M | Yes, procedurally, with limited tooling and no blending graph |

The honest read: the project's art pipeline is OBJ to static mesh, so P3 and P4 need a new skinned-asset pipeline that doesn't exist yet. P1 and P2 fit what is here today. I can't judge from here whether the new-asset path is affordable (open question 8).

### 4.2 Verified takeaways worth carrying forward

- **Upgrade cadence and short rounds** are the most-cited positives ("upgrades after every round", "a full run doesn't overstay its welcome") [WEB]. Ashen Spiral has rewards every wave and room already, so the mapping is about *how fast and how visible* they feel.
- **Dash as a defensive skill:** a 0.15 s parry window on dashing right before impact, and dash perks that freeze or shock on use [WEB]. Direct mapping to our dash (a "perfect dash" window and dash-triggered effects).
- **Transformative multipliers and chance-multipliers** (Dice Shot, Mega Crit, Slugger) create the "broken build" moments [WEB]. Mapping: trait metamorphoses at max rank and multipliers that stack with other traits.
- **Explosions that fall off toward the edge** were added "to deepen the combat feel" [WEB]. A tuning detail, not a structural idea.
- **High-risk perks** (Glass Cannon: +250% damage, -80% health; Cursed Lottery) [WEB] are a cheap way to offer risk-reward and make runs feel different.
- **Combo** is a counter capped at 5 that resets when you take damage, used by only a few perks [WEB]. Low-key, not a core system.
- **Community debate on permanent buffs** (they "trivialize the game") [WEB] is worth noting against our permanent upgrade tree.
